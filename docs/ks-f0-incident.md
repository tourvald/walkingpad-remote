## 1. Симптомы

- Две дорожки KingSmith **KS-F0 / F0** не останавливаются полностью: после Stop полотно ползёт на минимальной скорости (0.2–0.3 км/ч по KSFIT; 0.3–0.8 в наших логах).

- KSFIT начал показывать скорость в **милях** (раньше — км/ч).

## 3. Аудит нашего BLE-слоя (закрыт)

- Один-единственный `writeValue` (BluetoothManager), все команды через одну очередь.
- Единственный конструктор WalkingPad-кадров жёстко шьёт тип **`0xA2` (runtime)** — приложение **структурно неспособно** отправить `0xA6` (`set_pref_*` / NVRAM-запись).
- Вся поверхность: stop(speed-0) / set-speed / mode-manual / mode-standby / start + queryParams (read). На connect ничего не пишется.
- CRC корректен (сверен с ph4/QWalkingPad). Телеметрия пишет каждый write: `command_write` (hex, char_uuid, `command_source`), `controller_state`/`controller_manual_mode` в каждой строке (коммит `03db316`).

**Вывод:** записать persistent-настройку по документированному протоколу наше приложение не могло.

## 4. Протокольная карта KS-F0

**Кадры:** `F7 <type> … <crc> FD`, crc = sum(bytes[1:-2]) & 0xFF. Ответы начинаются с `F8`. Кадры с неверным CRC контроллер игнорирует.

**Runtime `0xA2`** (формат `F7 A2 cmd value crc FD`):
| cmd | value | Смысл |
|---|---|---|
| 0x00 | 0x00 | GET_STATUS (poll; QZ шлёт 1 Гц как noOp) |
| 0x01 | speed×10 | set speed; **0 = «стоп» в ph4-традиции** (но см. §8) |
| 0x02 | 0/1/2 | режим: AUTO / MANUAL («unlock» в QZ) / STANDBY (sleep) |
| 0x04 | 0x01 | **START/STOP toggle** («start_belt is actually toggle_belt»; у QZ — `start_pause`) |

**Persistent prefs `0xA6`** (формат `F7 A6 key 0 b2 b1 b0 crc FD`, NVRAM):
| key | Параметр | Источники |
|---|---|---|
| 0 | **query** (read-only, ответ = все параметры) | QZ init, QWalkingPad |
| 1 | target/goal | ph4 + QWalkingPad |
| 2 | **cali/regulate** («1=вкл калибровка, 0=выкл, но полотно продолжает ехать») | только QWalkingPad |
| 3 | maxSpeed | ph4 + QWalkingPad |
| 4 | startSpeed | ph4 + QWalkingPad |
| 5 | autoStart/intelligent | ph4 + QWalkingPad |
| 6 | sensitivity (1=high 2=med 3=low) | ph4 + QWalkingPad |
| 7 | display bitmask | ph4 + QWalkingPad |
| 8 | **units** (0=metric 1=imperial) | ph4 + QWalkingPad |
| 9 | childLock | ph4 + QWalkingPad |

Команды «reset to defaults» **нет** ни в одном источнике; откат = записать прежнее значение (поэтому сперва читать).

**Недокументированные** (видны в QZ-init = снифф KSFIT; мы НЕ шлём): `F7 A5 61 …` (handshake/профиль), `F7 B1 …` (похоже на дату/время), `F7 B3 …`. Диалект официального приложения шире известных prefs → поверхность для порчи persistent state больше.

**belt_state (`F8 A2`, байт 2):** 0 = stopped/idle · 1 = running · 5 = standby/sleep · 7, 9 = переходные при старте. QWalkingPad: `padRunning = s != 0 && s != 5`. Наша дорожка зависает в **s=1** → контроллер «считает, что бежит».

7. **Units/mph — открытый и важный тред** (§7): факт переключения произошёл и должен быть объяснён.
8. Никакого публичного отчёта о симптоме «Device Stopping»/creep не найдено — наш инцидент, видимо, первый задокументированный.

## 7. Units / mph — ОТКРЫТЫЙ тред

**Факт:** дорожка работала в км/ч → теперь KSFIT показывает мили, и `queryParams.unit = 1` (imperial) в NVRAM. Изменение произошло и требует объяснения; не закрываем как «display-only» без физического доказательства.

**Что возвращает `queryParams.unit`:** байт 13 ответа `F8 A6`; 0=metric, 1=imperial. На тестовой дорожке = 1.

**Как QZ учитывает unit при отправке speed:** **никак.** `forceSpeedOrIncline`: `speed[3] = qRound(requestSpeed * 10)` — км/ч×10 без какой-либо конверсии; парсинг скорости `packet[3]/10.0` — тоже без конверсии; A6-ответ QZ вообще не парсит; в файле нет ни `mile`, ни `1.60`. Конвертация миль у QZ — только на уровне UI-настройки приложения.

**Косвенные доказательства, что провод = км/ч независимо от unit:**
- QZ годами шлёт км/ч×10 на тысячи KingSmith-пад (включая imperial-сетапы в США) — жалоб на ×1.6 ошибку скорости в трекере нет.
- Наш лог 2: средняя командная скорость рампы 5.2 км/ч × 167 с ≈ 242 м — дорожка отдала 240 м (сходится при км/ч-физике).
- Длина шага: 382 шага / 240 м = 0.63 м/шаг (правдоподобная ходьба); при mph-физике 1.0 м/шаг (неправдоподобно).

**Поправка (2026-06-12) — дистанционная математика ЦИРКУЛЯРНА и ничего не доказывает.** Если прошивка в imperial-режиме исполняет wire-значения как mph И считает дистанцию в миль-скейленных единицах, числа сходятся точно так же: средняя 5.21 wire × 167 с при mph-физике ≈ 389 м, а 24 единицы дистанции × 1/100 мили = 386 м — совпадение не хуже километрового. Аргумент про длину шага тоже переворачивается: при mph-физике пользователь бежал, и 1.0 м/шаг для бега правдоподобен. Аргумент «у QZ нет жалоб» ослаблен: мы не знаем, какой unit зашит в NVRAM у дорожек QZ-пользователей. **Логи сами по себе юнит-агностичны; различить может только физика.**

**План физического доказательства (владелец):**
1. Экран самой дорожки: km/h или MPH?
2. KSFIT: есть ли тумблер units, переключается ли обратно, слушается ли контроллер.
3. Замер: команда «3.0» на 60 с → метка на полотне × длина полотна × обороты: **≈50 м = км/ч**, **≈80 м = mph**.
4. После units→metric (через физическое сервис-меню): повторный queryParams (ждём unit=0) + тот же замер.
5. queryParams со второй (рабочей/залипшей) дорожки → diff.

**Связанный риск:** даже при км/ч-проводе mph-режим мог исказить **записанные значения** prefs (maxSpeed 7.5 — кандидат), а наша телеметрия читает FE01-скорость как км/ч — если бы физика была mph, мы бы систематически занижали реальную скорость в 1.6 раза. На стоп-выводы это не влияет (state=1 — главный сигнал, юнит-независимый).

### 7.1 Units-scale mismatch — ОСНОВНАЯ гипотеза расхождения скорости (2026-06-12)

**Новое физическое свидетельство (владелец):** пик 3-минутного Test Run (команда «8.0») ощущался не как 7.5–8 км/ч, а как **≈12 км/ч** — заметно быстрее расслабленного бега. 7.5 mph = **12.07 км/ч** — совпадение точное.

**Числовой разбор обоих Test Run логов (11.06, 09:30 и 09:53) — идентичен:**
- отправлено приложением: `speed_target_kmh` max **8.0** · `speed_device_target_kmh` max **8.0** · payload `F7 A2 01 50` (raw **80**);
- получено от дорожки: `speed_reported_kmh` max **7.5** · `speed_reported_app_kmh` max **7.5**;
- **кламп на 7.5 подтверждён**: по 10 строк «команда 8.0 / эхо 7.5» в каждом логе;
- кламп **= `queryParams.maxSpeed` raw 75** байт-в-байт.

**Связка (рабочая модель):** приложение думает в км/ч → контроллер в imperial (`unit=1`, NVRAM) → wire-значения исполняются физически как mph → «7.5» едет как 12.07 км/ч → пользователь чувствует ~12. KSFIT показывает мили честно — это мы читаем провод как км/ч.

**Статус:** units-scale mismatch — основная гипотеза проблемы «скорость отображается/ощущается не так». Тяжёлый замер с меткой полотна **пока не требуется** — логическая связка подтверждена; финальная проверка = units→metric через сервис-меню (§10) + дешёвый 60-секундный замер из §10 фазы 5. **Это НЕ объясняет Stop/state=1** — стоп-тред остаётся отдельным.

⚠️ **SAFETY (до возврата metric):** если mph-физика верна, **все** наши команды скорости исполняются ×1.609: app-потолок «12.0» = физически **19.3 км/ч**, цели HR-алгоритма — в 1.6 раза быстрее задуманного. **Никаких HR-сессий и тестов с человеком на полотне на этой дорожке до units→metric.**

### 7.2 KSFIT cross-check (2026-06-12): две конкурирующие модели — статус CONTESTED

**Новый объективный факт:** KSFIT показывает `Maximum speed = 4.7 mi/h`. 4.7 × 1.609 = 7.56 км/ч = raw 75. KSFIT **интерпретирует raw как км/ч и конвертирует в мили для дисплея** — при mph-трактовке raw он показал бы «7.5 mi/h». Это прямо противоречит mph-физике из §7.1.

| Свидетельство | Model A: mph-физика (wire исполняется как mph) | Model B: км/ч-провод, units = только дисплей |
|---|---|---|
| Ощущение «ехало ≈12» на пике | ✅ объясняет точно (7.5 mph = 12.07) | ❌ необъяснено (7.5 км/ч — лёгкая трусца; субъективная ошибка?) |
| KSFIT `4.7 mi/h` = 7.5 км/ч | ❌ **противоречит** (показал бы 7.5 mi/h) | ✅ объясняет точно |
| `unit=1` NVRAM + мили в KSFIT | ✅ | ✅ (дисплейный слой) |
| F4=12 / F5=7.5 | ✅ пара km/mph одной скорости | ✅ спековый потолок 12 + активный лимит 7.5 км/ч |
| QZ шлёт км/ч×10 без конверсии, жалоб нет | ❌ против | ✅ за |
| Кламп 8.0→7.5 = raw 75 | ✅ (лимит в mph) | ✅ (лимит 7.5 км/ч — **вот функциональный баг**: спек 12, лимит почему-то 7.5) |

**Статус:** гипотеза §7.1 понижена с «основной» до **contested**. Объективная математика (KSFIT-дисплей) на стороне Model B; субъективная скорость — на стороне A. **Дешёвый физзамер снова обязателен** (60 с на «3.0»: ≈50 м = км/ч, ≈80 м = mph) — он единственный разрешит конфликт.

**Следствие Model B (если подтвердится):** реальная функциональная проблема скорости — **лимит maxSpeed=7.5 км/ч при спеке 12** (когда/кем выставлен — вопрос; KSFIT «Maximum speed» — возможный официальный канал вернуть 12 км/ч без BLE-хака). Units остаются косметикой дисплея + источником путаницы.

**KSFIT и запись units (по RE-данным):** в QZ-init (реплей сниффа KSFIT) записи units НЕТ; `set_pref_units` (key 8) существует в ph4/QWalkingPad — т.е. исторически какой-то официальный клиент его писал; текущий KSFIT для этого устройства **отказывается** (toast) → setter заблокирован capability-гейтом на стороне приложения. KSFIT — не recovery-path.

## 8. Toggle-stop — статус и инженерный комментарий

**Решение владельца (зафиксировано 2026-06-11):** toggle `F7 A2 04 01` — штатный stop/pause для KS-F0/R1Pro-family по QZ; наш прежний `speed=0` может быть неправильным stop-path для F0; для уже залипшего контроллера toggle recovery **не гарантирует** (KSFIT/пульт тоже не останавливают); рассматриваем как будущий правильный stop-path и отдельный controlled experiment — **не как доказанный фикс текущей поломки.**

**Противоречие (зафиксировано):** родной пульт — тоже toggle, и он не останавливает залипшие дорожки; KSFIT (BLE-клиент, чей stop почти наверняка тот же toggle — QZ реплеит его снифф) виснет на «Device Stopping». Значит **toggle по BLE фактически уже пробовался официальным приложением на залипших дорожках и не вывел контроллер из state=1.**

**Инженерное объяснение, когда BLE-toggle мог бы сработать при молчащем пульте:** пульт — отдельный RF-канал (свой приёмник/спаривание); если деградировал приёмник или слетело спаривание, нажатия вообще не доходят до state machine, а BLE-вход работает. Но у нас KSFIT по BLE тоже не останавливает → отказ в самой state machine контроллера, куда сходятся оба канала. **Честный вывод: «не должен сработать на уже залипшем контроллере, но нужен для полной матрицы»** — плюс отдельная ценность: toggle — кандидат на **штатный stop-path** на будущее (возможно, не вводящий контроллер в floor-состояние, в отличие от speed-0).

## 9. Правила безопасности (действуют)

1. **Никаких `0xA6`-записей / `set_pref_*`** до отдельного решения владельца. Только read (`queryParams`).
2. Никаких недокументированных кадров (`A2 03 07`, `A5`, `B1`, `B3`).
3. Никаких тестов скорости с человеком на полотне; рука на сетевом выключателе.
4. Изменения параметров — только через физическое сервис-меню по инструкции производителя, по одному, с фиксацией до/после.
5. Каждый стоп-тест → CSV → `tools/treadmill_analyzer/analyze_stop_sequences.py`.

## 10. План: безопасный возврат `unit` imperial → metric через физическое сервис-меню

*Одобренный канал изменения — только физическое меню. Через BLE не пишем ничего.*

**Фаза 0 — подготовка (до входа в меню):**
1. Полотно пустое; рука на сетевом выключателе; непрерывное видео дисплея+пульта со звуком (бипы важны).
2. Снимки «до»: наша Debug → Read Controller Params (скрин; ждём unit=1; записать, какая дорожка) · скрин KSFIT с милями · фото экрана дорожки (индикатор единиц, если есть).

**Фаза 1 — вход:** строго по инструкции KingSmith; каждое нажатие записывать (порядок нужен для выхода); **сфотографировать каждый экран до любого нажатия** (заодно полная инвентаризация параметров).

**Фаза 2 — идентификация параметра units:** искать `Unit / U-x / P-x со значением 0|1 / km|mi / Metric|Imperial` (на сегментном дисплее часто «0/1» или «kM»/«mi»). Контроль: текущее значение должно соответствовать imperial (=1). **Не уверены, что это units, — ничего не менять**: фото, выход, сверим с раскладкой A6 (key 8) и решим.

**Фаза 3 — изменение (одна переменная за сессию):** менять ТОЛЬКО units → metric (0/km). Ничего больше в этой же сессии (однопеременный эксперимент). Записать старое→новое; отметить, перерисовались ли числа на дисплее (напр., 0.2 → 0.3).

**Фаза 4 — выход + power cycle:** выйти штатно по инструкции (не рвать питание в момент записи NVRAM) → полное выключение выключателем ≥10 мин (рекомендация KingSmith) → включить.

**Фаза 5 — верификация (полотно пустое, в этом порядке):**
1. Экран дорожки: km/h?
2. Наша Debug → Read Controller Params: ждём `unit=0`; **ключевое — сравнить raw maxSpeed/startSpeed**: остались 75/5 или перескейлились (скажет, реинтерпретирует ли контроллер сохранённые prefs при смене units).
3. KSFIT: единицы? поведение «Device Stopping»?
4. Пульт: старт → 2.0 → стоп с пульта: доходит ли до 0, уходит ли state=1 (рука на выключателе).
5. Units-scale замер: «3.0» 60 с → ≈50 м (км/ч) vs ≈80 м (mph).
6. Короткий Test Run из нашего приложения → Export CSV → stop-forensics + diff params.

**Чего не делать:** не менять cali/regulate, maxSpeed, sensitivity и безымянные параметры в той же сессии; не делать одновременно на обеих дорожках (сначала тестовая → верификация → решение по второй); никаких BLE-записей.

**Дерево решений по результату:**
- `unit=0` + KSFIT в км/ч + стоп заработал → порча units была причастна; следующими однопеременными шагами восстанавливаем maxSpeed/startSpeed.
- `unit=0`, но стоп всё равно залипает → units ≠ причина стопа (как и подозревали); остаётся controller-side → эскалация в KingSmith с полным досье.
- units не меняется / откатывается после power cycle → **порча NVRAM подтверждена** — главный факт для эскалации производителю.

## 11. Physical service menu params (2026-06-12)

**Официальные инструкции KingSmith (от поддержки, дословно):**
1. *Factory test mode:* удерживать start/stop + mode на пульте до появления `test` на дисплее. `mode` листает шаги. `plus`, затем короткое `start/stop` — запуск **no-load test** (⚠️ лента поедет). Выход — `mode`.
2. *Parameter adjustment mode:* удерживать центральную кнопку пульта при включении питания. `mode` листает данные. «Сверить значения с **reference video**», выход — короткое нажатие центральной кнопки. → **У поддержки есть reference video с эталонными значениями — запросить!**

**Снятые владельцем экраны parameter mode (цикл 1):** F1=075 · F2=22 · F3=160 · F5=7.5 · G01=001. F4 не снят.

**Цикл 2 (2026-06-12) — полный + изменяемость кнопками пульта:**
F1=075 (изменяемо) · F2=22 (изменяемо) · F3=160 (изменяемо) · **F4=12 (изменяемо, найден)** · F5=7.5 (изменяемо) · **001=011 (НЕизменяемо)**.
Уточнено владельцем: **«001» — имя экрана, «011» — его значение.** Неизменяемость = это **не настройка** (read-only инфо-экран, вероятно версия/код), а значит **units-переключателя в parameter mode НЕТ.**

**KSFIT-скрины (2026-06-12):**
- Экран устройства: **`Maximum speed = 4.7 mi/h`**. Математика: 4.7 mi/h × 1.609 = **7.56 км/ч** ≈ raw 75. → **KSFIT интерпретирует raw 75 как 7.5 км/ч и конвертирует в мили для отображения** (иначе показал бы «7.5 mi/h»). Объективный аргумент за км/ч-провод (§7.2).
- Экран **Unit**: варианты Metric/Imperial, выбран **Metric** — при этом скорость на экране устройства в **mi/h** (две несинхронные прослойки: app-level настройка vs controller-level unit=1).
- Попытка переключения → toast: *«The current device does not support setting the imperi…»* → **KSFIT не умеет/отказывается писать units для этого устройства** → KSFIT **не является recovery-path для units**.

**Ключевой вывод цикла 2:** F4=12 + F5=7.5 — **одно и то же значение спекового максимума в км/ч и mph** (12 км/ч = 7.46 mph). Контроллер хранит оба представления; активный wire-лимит F1=075 соответствует **mph-представлению** → ещё одно независимое подтверждение mph-модели (§7.1). **Units-переключателя в parameter mode не видно** → возврат metric этим меню, вероятно, невозможен; пути: настройки KSFIT (приоритет — проверить), прямой вопрос поддержке, BLE `set_pref_units` (запрещён до отдельного решения владельца).

**Связь с симптомами:** F1/F5/G01 в связке объясняют units/mph, кламп 7.5 и расхождение скорости (§7.1). **Ни один снятый экран не объясняет Stop/state=1 и creep** — экрана cali/regulate в снятом цикле нет (в NVRAM cali=0).

**Несоответствия → аргумент за повторный полный цикл фото:** в queryParams есть `startSpeed=5 (0.5)`, `sensitivity=2`, `childLock=0`, `cali=0` — ни одного экрана с такими значениями не снято. Гипотеза: **F4 ≈ startSpeed (005/0.5)** — пропущен; после G01 могут быть G02+. Нужно: листать `mode` до зацикливания, фотографировать каждый экран, посчитать полную длину цикла.

### Безопасность работы с меню
- **Можно менять (контролируемо, по §10):** только G01 — один шаг, обратим, проверяем по BLE-чтению: flip 1→0 → выход → power cycle → `Read Controller Params`: `unit=0` → это units (профит); `unit=1` → это был язык/другое → вернуть G01=1.
- **Не трогать:** F2, F3 (нет расшифровки, нет NVRAM-аналога → моторные/сенсорные внутренности), F1/F5 (при mph-физике 75 — вероятно **корректный** спековый максимум, не порча).
- **В parameter mode листать только `mode`; +/− не нажимать** (вероятно, редактируют текущее значение). Выход — короткое нажатие центральной кнопки.
- **В factory test mode не нажимать `plus` + `start/stop`** (запуск no-load — лента поедет), если прогон не планируется.
- Перед любым изменением — приоритетно **спросить поддержку: какой экран = units на KS-F0** и получить **reference video** (эталонные значения).
